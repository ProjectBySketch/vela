# 24 — Security

**Status:** `spec`. Related: doc 09 (§7 `unsafe`), doc 14 §6 (web defaults), doc 17
(FFI boundary).

Security in Vela is not a library you add; it is four defaults that a program has
to opt *out* of, and one declaration (`[permissions]`) that says what a program
may touch at all.

---

## 1. The four defaults

| Default | Meaning | Opt out |
| --- | --- | --- |
| **No ambient authority** | a program can only reach what `vela.pkg` declares | declare a permission |
| **Memory safety** | no `unsafe` outside `sys`, no reasoning required | `#![deny(unsafe)]` makes it provable; `unsafe` requires a reason string |
| **Escaping by construction** | `Str` is never HTML, SQL or a path | `Markup.trust`, bound SQL params, `path.join` |
| **Fail closed** | a missing secret, certificate or permission stops the program at startup | none |

---

## 2. Permissions

```toml
[permissions]
filesystem = { read = ["data/**"], write = ["data/**", "logs/**"] }
network    = { hosts = ["api.acme.com", "*.acme.com"], protocols = ["https"] }
env        = ["ACME_*"]
process   = false
camera    = true
microphone= true
screen    = false
location  = false
contacts  = false
photos    = { read = ["user-selected"] }
```

Rules:

* An empty `[permissions]` block means **no** filesystem, network, environment,
  camera or process access. `fs.read` outside the declared patterns is
  `E-SEC-010` at run time (and, for a literal path, `E-SEC-010` at compile time).
* A dependency's permissions are the intersection of its declaration and the
  application's: a library cannot widen what the app asked for. The build fails
  if a dependency requires a permission the app does not have (`E-SEC-011`,
  listing the dependency path and the call site).
* On Apple platforms, the declarations map to entitlements and Info.plist usage
  strings, generated by the build; on Linux, to a seccomp/landlock profile; on
  web, to what the browser requires at the API call. One declaration, enforced
  three ways.
* Changing a permission is a feature: a package may declare `permissions` per
  feature, and `vela build --features` prints the effective set.
* `vela build --audit` prints the table (below) for the whole dependency tree, so
  a supply-chain review is one command.

```
package                 fs            network            process  env
acme/app                data/**       api.acme.com       no       ACME_*
acme/http               -             *                  false    -
acme/db                 -             -                  false    -
acme/logger             logs/**       -                  false    -
```

## 3. Secrets

```vela
let key = try secrets.get("STRIPE_KEY")?      // Secret<Str>, never printed
let sig = crypto.hmac(secrets.require("SIGNING_KEY"), body)
```

* A `Secret<T>` prints as `***` through `Display` and `Debug`, is excluded from
  JSON serialisation (`E-SEC-020` if a type with a `Secret` field derives `Json`
  without `#[json(skip)]`), and is redacted in logs, panics and error messages.
* `secrets.require` fails at startup if missing (`E-RUN-080`), because a service
  that boots without a key is a service that fails on the first request.
* The source is the platform's store: Keychain on Apple, `systemd-creds` /
  `pass` / environment on Linux, nothing on web (variables come from the server).
  A `.env` file is read only when `[permissions] env` allows it and only in
  development builds (`W-SEC-010` in release).
* A secret never crosses the wire in a `Markup` or a URL; `url.withSecret` does
  not exist.

## 4. Untrusted input

Five categories, each with exactly one safe constructor:

| Input | Safe path | Bypass (audited) |
| --- | --- | --- |
| HTML | `html.*`, `Markup` (escapes) | `Markup.trust` — `E-WEB-020` in a `web` module |
| SQL | `#[query]` with bound params | `queryRaw` — `W-DB-010` |
| paths | `path.join(base, userPart)` refuses `..` and absolute parts | `path.unsafeJoin` |
| headers / cookies | typed accessors, length limits | `req.rawHeaders` |
| URLs | `url.parse` + `url.sameOrigin` for redirects | `fetchUnchecked` |

`path.join` returns `Result<Path, PathError>` and is total: a user-supplied
segment can never escape the base. That single signature removes traversal from
the list of things to remember.

## 5. Capabilities per profile

| Capability | `core` | `app` | `web` | `sys` |
| --- | --- | --- | --- | --- |
| filesystem | declared | app sandbox | none in client, declared on server | none |
| network | declared | declared | declared (fetch/CORS) | none |
| camera / mic | declared | declared + OS prompt | browser prompt | device-specific |
| screen capture | declared | declared + OS prompt | browser prompt | none |
| process spawn | declared | forbidden | forbidden | kernel-provided |
| `unsafe` | allowed with reason | allowed with reason | denied by default | expected |
| dynamic loading | forbidden | `#![plugins]` only | none | none |

A capability that does not exist for a profile is not "denied at run time" — the
module is not compilable (`E-MOD-060`).

## 6. Cryptography policy

```toml
[crypto]
minTls         = "1.3"
minRsaBits     = 2048
minAesBits     = 256
allowSha1      = false
allowMd5       = false
allowEcb       = false
passwordHash   = "argon2id"
```

The build reads the policy and refuses a program that calls a disallowed
primitive (`E-SEC-030`) — it is a *compile-time* policy, not a lint, because a
deprecated cipher in a binary is a finding in an audit, not a review comment.

`crypto.constantTimeEq` is the only comparison provided for tokens; `==` on two
`Secret<Bytes>` is `E-SEC-031` so timing leaks do not get written by accident.

## 7. Supply chain

| Measure | Status |
| --- | --- |
| lock file with content hashes | `spec` (doc 08 §5) |
| `vela build --frozen` in CI | `spec` |
| `vela audit` (advisories for dependencies) | `planned` |
| package signing (sigstore or a registry key) | `planned` |
| reproducible builds (byte-identical artifacts) | `spec` |
| SBOM emission (`vela build --sbom cyclonedx.json`) | `planned` |
| vendoring and offline builds | `spec` |
| deny-list of packages in `vela.pkg` | `spec` |

A build prints its inputs: compiler version, every dependency with its hash, the
permission set, and the flags. `vela build --print-config` emits that as JSON for
a CI job to diff against the approved set.

## 8. Sandboxing

* **Apple**: the generated Xcode build enables the App Sandbox when the package is
  `app`, with entitlements derived from `[permissions]`; a permission the package
  declares but the entitlement does not grant is a build error against the
  provisioning profile (`E-SEC-040`).
* **Linux servers**: `vela run --sandbox` installs a seccomp filter built from the
  permission set, plus a landlock ruleset for the declared paths. A syscall outside
  the set kills the process with a diagnostic naming it.
* **Web**: the client is WASM in the browser's own sandbox; nothing extra needed.
* **Plugins** (doc 31): each plugin gets its own instance with its own permissions,
  and a plugin that exceeds them is terminated, not trusted.

## 9. Logging and error hygiene

* An error message never includes a `Secret`, a session token, a full request
  body, or a stack trace of a foreign frame (`E-SEC-050` in a `web` handler that
  formats a `Secret` into a response).
* `log.*` redacts fields typed `Secret` and any key whose name matches
  `password|token|secret|key|authorization` (configurable).
* Panic messages in `web` are replaced by a generic 500; the detail goes to the
  log with the trace id.
* Timing: a login endpoint's failure path must take the same code path as success
  (`crypto.constantTimeEq` plus a dummy hash), and `vela check --security` flags
  an early return before a comparison.

## 10. Threat models per profile

| Profile | Primary threats | Mitigations that are language-level |
| --- | --- | --- |
| `web` server | injection, SSRF, CSRF, XSS, path traversal, deserialisation | typed SQL, address policy, tokens in `form()`, `Markup`, `path.join`, `Json` derives |
| `web` client | XSS through the DOM, supply chain | no `innerHTML`, WASM sandbox, lock file |
| `app` | malicious document, permission overreach, crash with secrets in logs | sandbox, capability declarations, redaction |
| `core` | dependency compromise, argument injection | no shell unless asked, permission set, lock hashes |
| `sys` | memory corruption | `unsafe` audit mode, `#![deny(unsafe)]` per module, `--audit` counting |

## 11. Auditing tools

| Command | Output |
| --- | --- |
| `vela build --audit` | permissions × packages table, `unsafe` blocks with reasons, `asm!` count, FFI surface |
| `vela check --security` | the lint set in §9 |
| `vela audit` | dependency advisories (`planned`) |
| `vela build --sbom` | CycloneDX document (`planned`) |
| `vela fuzz` | property-based fuzzing of a target function (`planned`) |

The `unsafe` audit is the one that matters most for a systems program:

```
$ vela build --target x86_64-unknown-none --audit
module              unsafe blocks   asm!   extern   reason coverage
kernel/mmio                    12      0        0   100%
kernel/sched                    3      2        0   100%
kernel/boot                     1      4        0   100%
total                          16      6        0   100%
```

Every `unsafe` block without a reason string is `W-MEM-010`; this table is how a
kernel's safety argument is reviewed line by line instead of in prose.

## 12. Diagnostics

| Code | Meaning |
| --- | --- |
| `E-SEC-010` | access outside the declared permission |
| `E-SEC-011` | dependency requires a permission the app does not grant |
| `E-SEC-020` | `Secret` in a serialised structure |
| `E-SEC-030` | disallowed cryptographic primitive |
| `E-SEC-031` | non-constant-time comparison of secrets |
| `E-SEC-040` | declared permission not granted by the provisioning profile |
| `E-SEC-050` | secret or token formatted into a response |
| `W-SEC-010` | `.env` loaded in a release build |
| `W-SEC-020` | `Markup.trust` used anywhere |
